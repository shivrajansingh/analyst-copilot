Token usage & cost docs/mocks/token-cost.html

What this mock is asserting

  • Cost belongs to the answer, not beside it. The strip is a footer on AnswerCard, below the citations and below the agent trail — the last thing read, because it is the least important thing on the card and the card must not start with a price.
  • No state colour. Nothing here is verified, declined, failed or building. Those four mean the system proved / declined / errored / is indexing, and a cost is none of them. Only ink, ink-muted, ink-subtle and accent appear.
  • An estimate never looks like a measurement. When the provider omits usage the figure carries a ~ and a dotted underline, and the footnote says so in words.
  • No price is better than a wrong price. An unpriced model shows tokens and says no price configured. It never guesses a rate.
  • Headline 4dp, rows 6dp. The headline is read at a glance; the rows are compared against each other, where $0.0001 would collapse four distinct stages into one number. Tabular numerals keep the decimal points aligned.
  • Every row names the model that ran it. A run uses two — a chat model and an embedding model at a hundredth of the price — and a table of costs that does not say which is which cannot be checked against a provider's bill.
  • The header names the model that spent the most, not the first one used. The query embedding runs before any chat call, so "first" is reliably the cheapest thing in the run — naming it hides the model doing 99.99% of the spending. Attribution is read off the stage, not inferred.
  • A cost below a micro-dollar is <$0.000001, never $0.000000. Money is carried as integer micro-dollars, so the query embedding arrives as an exact zero — and a row of zeros reads as "free" rather than "too small to write down".
  • The row background is the share of cost. A deep run is ~71% reader fan-out, and that should be visible without a chart or a second colour.
